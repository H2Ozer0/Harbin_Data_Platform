## 核心改变

### 1️⃣ 工期调整
- **原计划**：5天 (理论 40h)
- **新计划**：7个工作日 (实际 56h 可用)
- **理由**：63h任务 → 需要充足的buffer和冒烟时间

### 2️⃣ 工时重新分配
| 人员 | 原计划 | 新计划 | 变化 | 说明 |
|------|--------|--------|------|------|
| P1 | 18h | 22h | +4h | 增加联调与最终修复缓冲 |
| P2 | 23h | 29h | **+6h** | **Julia ETL重估：6h→10h**，压缩重复测试 |
| P3 | 22h | 27h | +5h | 集成主导 + 收尾文档 |
| **总计** | **63h** | **78h** | +15h | 现实工时 |

### 3️⃣ 执行节奏
- 第一步：所有人先创建自己的 feature 分支，再开始开发
- 第二步：P3 先搭框架和共用状态，P1/P2 并行开发各自功能
- 第三步：P3 提前做一次集成冒烟，尽早暴露冲突和接口问题
- 第四步：各人根据冒烟结果修复，P3 继续收口集成
- 第五步：P3 主导回归测试和最终合并

### 4️⃣ 新增关键工作项
- **阶段 1**：API 合同 + ADS 建表验证 + dashboardStore.js 共用框架设计
- **阶段 4**：**提前集成冒烟测试** ← 新增，规避后期 panic
- **阶段 6-7**：**扩展回归测试** ← 新增，确保 6 个页面稳定性

## 关键变化点

### 变化1：Julia ETL 被重视

**旧方案**：
```
Task 9: Julia ETL - 6h (严重低估)
```

**新方案**：
```
Task 9: Julia ETL - 10h
  - 理解ODS结构 + 验证数据 (1.5h)
  - 设计+实现算法 (2h)
  - 测试 + 边界情况处理 (3h)
  - 性能优化 (2h)
  - 集成测试 (1.5h)
```

### 变化2：新增提前冒烟测试

**新增工作**：P3 在中期独立进行提前集成冒烟
```
目标：在正式提交前，发现并记录主要集成问题

流程：
1. P3 创建 feature/integration-smoke 分支
2. 合并 P1/P2 当前分支（即使不完全）
3. 修复明显编译/链接错误
4. 跑所有API端点（mock数据）
5. 检查前端6页面是否可访问
6. 记录问题，反馈给P1/P2
7. P1/P2 基于反馈修复

好处：避免后期手忙脚乱的 panic 修复
```

### 变化3：明确代码所有权（减少 merge 冲突）

**DashboardController/Service/Repository 所有权**：
- P1 负责写：`congestion/*` 方法、`kpi/*` 方法、`comparison/*` 方法
- P2 负责写：`hotspot/*` 方法、`driver/*` 方法、`rest_location/*` 方法
- P3 负责写：`catalog/*` 方法、`lineage/*` 方法、`quality/*` 方法
- **最终版本决定权**：P3（通过PR制度）

**冲突处理**：
```
如果P1/P2需要修改共用部分（如基类、异常处理、工具类）：
→ 必须先和P3沟通
→ P3负责验证不破坏其他功能
→ 统一合并到main
```
